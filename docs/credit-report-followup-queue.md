# Credit-report follow-up queue: operations and recovery

## Behavior

- A database trigger stamps each committed receipt with the database time and, once all three distinct bureaus are present for a contact, records the receipt in a private metadata table in the same transaction. The deadline is exactly 48 elapsed hours after that timestamp, including weekends and holidays.
- Each qualifying receipt has one idempotent trace row keyed by its immutable receipt ID. An open contact obligation is reused and its due time is reduced to the earliest qualifying deadline. A full-set replacement after a completed contact opens a new obligation. Existing contacts and a third PDF added later follow the same path. Partial sets create no obligation.
- Upload receipt commit and queue capture share one database transaction. A failed trigger rolls back the receipt. If receipt commit succeeded but finalization or the HTTP response was lost, the obligation remains. Upload reconciliation also calls the idempotent capture routine, and the CRM reconciliation endpoint scans current full sets for a missing latest-receipt trace.
- The default assignee is the contact's current non-readonly CRM owner; if absent, it is the oldest CRM admin. If no eligible user exists, the obligation remains visible as unassigned instead of blocking a valid report receipt. Staff and admins can assign/reassign it; every change is audited. No primary/backup schedule is encoded, so owner sign-off and seven-day coverage remain required before production use.
- A recorded `reached` outcome closes the obligation with the actual contact time, channel, actor, and outcome. `no_answer`, `left_message`, and `other` are retained attempts and leave it open. No customer email, SMS, booking, analysis, or other delivery is triggered.

## PDF privacy, purge, and retention

Queue tables contain contact ID, bureau, receipt UUID, receipt/deadline timestamps, obligation state, assignee, and contact outcomes. They do not contain report bytes, storage paths, signed URLs, report contents, or file names. The CRM link opens the existing contact page, which retains its current contact-scoped report authorization.

Recoverable CRM trash keeps the follow-up metadata, consistent with report retention, and the inactive contact is not listed in the queue. The queue tables avoid a direct contact foreign key for this reason; a write guard requires an active contact. Permanent contact purge explicitly deletes the obligation, and its receipt traces, outcomes, and assignment audit rows cascade from it in the database purge. Existing report-file deletion and late-upload reconciliation still govern PDF bytes.

Queue metadata is retained while the contact is active or in recoverable trash, including completed outcomes, and is removed on permanent contact purge. There is no time-based purge job in this bounded implementation. A legal/privacy owner must approve any shorter retention period before production. Previously downloaded CRM backup files are separate copies and are not erased by a contact purge; store them with restricted CRM-backup access and delete them under the owner's approved backup retention schedule.

Full CRM backup format v3 includes active-contact queue obligations, receipt traces, contact attempts, and queue audit, but no PDF data. Queue rows for recoverable-trash contacts are omitted because the existing full backup does not export trash entries. Exported current assignee and actor IDs are cleared, and assignee UUIDs are removed from audit before/after snapshots; audit action, timestamp, and immutable actor display-name snapshots remain. On restore, open obligations are visible as unassigned and must be reassigned. Versions 1 and 2 remain importable and restore an empty queue; before restoring one, take a v3 backup or transfer all active obligations because the older format cannot carry them. Full restore replaces active-contact queue metadata together with CRM contacts; it does not restore private PDF objects, which remain governed by the existing report-storage recovery process.

The admin-only contact privacy JSON export also includes that active contact's queue obligations, receipt traces, contact attempts, and audit. It excludes PDF bytes, storage paths, filenames, and upload session/attempt metadata, and clears staff UUIDs as in the v3 full backup. A missing or trashed contact still has no active-contact export.

## Migration and rollback

Migration `20260927120000_credit_report_followup_queue.sql` is additive apart from the upload receipt timestamp trigger, the existing upload reconciliation function extension, and backup export/restore versioning. It backfills one event for each contact's currently latest receipt when all three bureaus are present. Earlier replacement history cannot be reconstructed because the previous schema stored only one row per bureau.

Before applying in any environment, take and retain the current CRM backup, confirm the existing report-storage backup and purge procedure, then apply the migration transactionally. Immediately after migration, export and verify a v3 CRM backup, which is only available after this migration, and run `supabase/tests/credit_report_followup_queue.sql` plus the existing credit-report reconciliation SQL test. The queue SQL exercise includes same-session bureau replacement through the `(session_id,bureau)` conflict-update path and checks that the replaced receipt keeps a trace without extending the earliest open deadline. Exercise competing qualifying receipts on separate database connections before production; the single-transaction SQL exercise does not verify concurrency behavior. Verify the due-order list, assigned users, and backup round-trip with synthetic contacts before enabling staff use.

For an application rollback, first export the v3 queue backup and transfer every open obligation and due time into a verified owned manual/CRM task; then confirm the staffed manual process covers new receipts before disabling queue capture or reverting the queue UI/API. Do not drop queue tables while open obligations exist. When capture is re-enabled, replay receipt reconciliation and compare the manual tasks with queue obligations so staff do not contact the same person twice. If a schema rollback is required, reconcile all full-set receipts, transfer and verify every open obligation, then disable the two `credit_report_followup_receipt_*` triggers and remove queue RPCs/tables in a separately reviewed migration. Reinstating the feature after that requires restoring the v3 queue backup and replaying receipt reconciliation before staff rely on the queue. No production migration or rollback is run by this change.

## Launch dependencies

The public credit-check page and upload interaction are unchanged. Production use still requires separate approval, independent QA, named weekend/absence backup, check cadence and escalation, privacy retention sign-off, and verification of CRM role membership and private report access. This code alone is not evidence that a contact was reached or that staffing coverage exists.
